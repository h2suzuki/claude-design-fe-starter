# 実装前ヒアリング — mock に写らないことを聞く

mock は「何がどう見えるか」の正本だが、**「どれだけあるか・どれだけ待つか・どこから来るか」は写らない**。実装に入ってから聞くと作り直しになるので、画面の実装を始める前に一度で聞く。

聞く相手は発注側（画面の使われ方を知っている人）。答えは発注書か PR 説明に残し、`screen-loop.md ④` の完了条件にする。

**機械で分かることは聞かない。** mock 自身の破れ（横スクロール・はみ出し・重なり・文言や token の割れ）は凍結時の検査で出す（`docs/presentation/ui-mock/README.md` の凍結手順）。ヒアリングは人しか知らないことに絞る。

## 初回のみ（walking skeleton で 1 度）

**外部依存**

- 地図・動画・SNS の埋め込みはあるか。遮断された環境では何を見せるか
- 外部が落ちているとき、画面全体を止めるか、その領域だけ畳むか

> 埋め込みは export の閉包に入らない。mock 側も実装側も同じく空になるので、parity は通ってしまう。

**権限と出し分け**

- ログイン状態や role で表示が変わるか。mock はそのうちどの状態を描いているか

> mock は 1 つの状態しか描かない。描かれていない状態は「無い」のか「描いていないだけ」なのか、mock からは区別できない。

**遷移と保持**

- 戻ったときにスクロール位置・入力・選択を保つか

## 画面ごと（実装に入る前）

**重い資産**

- この画面で読み込みが重くなりそうなものはどれか（大きな画像・拡大表示・動画・地図）
- 画像の解像度を落としてよいか。落としてよい下限はどこか
- 開いた時点で裏で読むか、操作されてから読むか

> mock は資産を原寸で参照する。実測例: 拡大表示用の PNG 4 枚が計 14.1 MB で初回表示が体感で待たされた。JPEG 化で 1.74 MB、開いた 300ms 後に先読みして、クリックから表示まで 35〜70ms になった。**この判断は見た目を変えないので mock には現れない。**

**量**

- リストや表は実際に何件並ぶか。「多い」のは何件からか
- 文字列の実際の最大長はどれくらいか（人名・住所・名称）
- 空になることはあるか

> mock が描くのは数件・短い文字列の「見本」で、実データの分布ではない。件数と長さは、折り返し・省略・スクロールの設計を変える。

**状態の実際**

- 空・エラー・読み込み中は実際どのくらいの頻度で起きるか
- 読み込みが長引いたとき、待たせるか、部分的に見せるか

> mock には全状態が並ぶが、頻度は描かれない。滅多に出ない状態と常時出る状態では、置く場所も作り込みも変わる。

**入力（入力がある画面のみ）**

- 必須・形式・上限の規則
- 送信に失敗したとき、入力した内容を保つか

> mock が描くのは error 状態の**見た目**であって、何が error なのかの規則ではない。

## 書き方

- **答えが「決まっていない」なら、そう書く。** 空欄のままにすると、実装が既定値を勝手に決めて既成事実になる
- 数値は数値で受け取る（「速く」ではなく「クリックから 100ms 以内」）。後から検証できる形にする
- 発注側が判断できない項目（技術的な選択肢が要るもの）は、選択肢と各々の帰結を添えて聞き直す
